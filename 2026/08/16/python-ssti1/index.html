0x02 重点分析 app.py

逐行审计，找出漏洞点。

①：render_template_string

Flask 渲染模板有两种方式：

· render_template(‘index.html’, name=name) —— 从文件加载，安全，用户数据通过参数传递。
· render_template_string(str) —— 直接渲染字符串，字符串里的 {{ }}会被解析成 Python 表达式执行。

这里用的是第二种，意味着模板引擎会将字符串内容当作代码来解析执行。

②：用户输入直接拼入模板

name 是 POST 请求中用户提交的参数，未经任何过滤，直接被 f-string 拼接到字符串 str 中。而这个 str 随后被交给 render_template_string 渲染。

用户输入的内容会变成模板代码的一部分被执行 —— 属于典型的 SSTI。

攻击者只需要通过 POST 方式提交 name 参数，就可以向模板中注入任意 Jinja2 语法。

0x03 攻击代码原理解析

3.1 攻击代码

当用户输入被拼进模板字符串时，Jinja2 会把 {{ }} 里的内容当成代码执行。攻击者利用 Python 的对象内省机制，从 self 一路追溯到 os.popen，最终执行系统命令读取 flag。

3.2 .popen

服务端接收 name 之后，把它拼进了模板字符串 , 然后交给 render_template_string 渲染。

因为在 Jinja2 的模板执行环境里，os 这个模块默认没有被导入。所以如果直接写 os，模板引擎根本不知道这是什么。

os.popen 是 Python 标准库 os 模块中的一个函数，全称 pipe open（管道打开）。它在一个子进程中执行 Shell 命令，并返回一个用于读取该命令标准输出的类文件流对象。调用 .read() 方法可以获取命令执行后的输出内容。

3.2一点个人理解

这道题让我对“注入型漏洞”有了更本质的认识：

SSTI 和 SQL 注入、命令注入本质上是同一类问题——用户输入被放进了“解释器”的上下文里，而解释器没能区分“数据”和“代码”。在 SQL 注入里，数据被拼进了 SQL 语句；在 SSTI 里，数据被拼进了模板字符串。

防御的核心，就是切断这条链——不让用户输入有机会进入模板引擎的解析范围。

对比维度 SQL 注入 SSTI
攻击目标 数据库 Web 服务器
最终危害 数据泄露、权限绕过 远程代码执行（RCE），直接控制服务器
入口点 SQL 语句中的查询参数、表单等 模板渲染函数（如 render_template_string）
产生原因 将用户输入拼接到 SQL 语句 将用户输入拼接到模板字符串
典型防御 参数化查询（PreparedStatement） 使用 render_template 并传参
危害等级 ⚠️ 中高危（取决于数据库权限） 🔴 高危（可直接执行系统命令）
